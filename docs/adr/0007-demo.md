## Context

The PRD and the Design Doc planned a public demo: Gradio on a free Hugging Face Space running on CPU (G5, M5, deliverable 5, D7). The current Hugging Face documentation says that creating a Gradio or Docker Space requires a paid plan (PRO for personal accounts); the only free exception is up to two Gradio Spaces on ZeroGPU for personal accounts with a verified email and an age over 30 days. Static Spaces are free but cannot run the model server-side. The project has no budget for paid services (PRD §9) and 13 days remain.

## Decision

1. **v1 demo is local:** a Gradio app on the project machine, serving on `127.0.0.1` only, using the GPU if present and the CPU otherwise, with the same tokenizer and generate code as the pipeline.
2. **Features:** right-to-left prompt, sliders for temperature, top-k, and max new tokens, seed, six example prompts, streaming output with a Stop button, the normalized prompt, a token view, and a limitations text (English and Arabic) shown directly above the output.
3. **Limits:** prompts of at most 100 tokens, at most 200 new tokens, defaults 0.8, 40, and 80.
4. **No logging, no telemetry, no content filter.** On the CPU, a warning is shown when max new tokens is above 100.
5. **No KV cache in v1.**
6. **Publication is optional and after v1,** documented in `09` §9: a ZeroGPU Space from a personal Hugging Face account older than 30 days, and the weights as a model repository only.
7. **PRD changes:** G5 becomes a local interactive demo; M5 becomes "the local demo returns a continuation in under 10 s for prompts up to 100 tokens on the project machine"; deliverable 5 becomes a local demo with a screen recording or GIF in the README (proposed edits, `09` §12).

Reasons:

- The free CPU Space the plan relied on no longer exists, and the only free Gradio route (ZeroGPU) needs an eligible account and extra code. A local demo needs neither and still meets FR7 and FR8.
- Measured on the prototype, the default settings run in 0.74 s on the project GPU and 5.2 s on two CPU threads, so M5 holds on the project machine without a cache.
- Local serving keeps prompts on the machine, which is the simplest way to keep UR7 (no logging) true.

## Alternatives considered

| Alternative | Outcome | Why |
|---|---|---|
| Gradio on a free Hugging Face CPU Space | Not available | Needs a paid plan to create |
| Gradio on ZeroGPU as the v1 deliverable | Deferred (author) | Free, but needs an eligible account, `@spaces.GPU`, and a version-checked environment; visitors depend on a GPU quota; the host's logging cannot be controlled |
| Hugging Face PRO | Rejected | PRD §9: no paid services |
| `share=True` public link from the laptop | Rejected | Exposes the machine and the prompts |
| Static Space with in-browser inference | Not planned | The tokenizer would have to be ported to JavaScript; breaks the rule that the demo reuses the pipeline's code |
| KV cache now | Deferred | Verified equal to the full forward pass (1.3e-5) and 4 to 8 times faster at 200 new tokens on a CPU, but unnecessary on the GPU and one more place for a silent bug |
| A content filter | Rejected (PRD NG8) | Out of scope; the warning is the limitations text and the Model Card |
| Streamlit or a custom front end | Rejected | Design D7, PRD NG7 |

## Consequences

**Positive**

- No account, host, or cost is needed to finish v1; nothing the demo does leaves the machine.
- The interface is verified against the actual Gradio version (argument names, streaming, error propagation), and the prototype already shows the main behaviours.

**Negative and risks**

- **Nobody else can try the demo** without running it. The README's screen recording or GIF carries the presentation; goal G5 as originally written is not met.
- **Gradio telemetry is on by default** and must be disabled explicitly; other network calls at start-up were not audited.
- **On a CPU, long outputs break the 10-second target** (17.5 s for 100 + 200 tokens on two threads). The target is defined for the default settings and for the project machine; the app warns when it runs on a CPU with max new tokens above 100.
- **Gradio 6 moved `theme` and `css` to `launch()`;** a different major version may move more, so the version is pinned.
- **The Arabic texts of the interface are drafts** until a native speaker reviews them.
- **Publishing later** needs the account conditions of `09` §9 to still hold; they were read on 2026-10-09 and can change.

**Changes this decision requires**

- Edits to the PRD (G5, M5, deliverables 4 and 5, §1, §5, §11), the Design Doc (D7, §4.7, the flow diagram, the artifacts table), the README, and `CLAUDE.md` (flagged, not applied): see `09` §12.
- `app/app.py`, `app/limitations.md`, and `test_app.py`, written test-first; `gradio==6.30.0` in `requirements-dev.txt`.

**Limits of the evidence**

- The prototype used the pilot model, not the final one; the latency of the final model with its final vocabulary is to be re-measured.
- The Hugging Face documentation is a moving target; the statements are as of 2026-10-09.
- The CPU latencies were measured on this laptop's cores, not on a Hugging Face host.

## Revisit triggers

1. The author decides to publish: follow `09` §9 and revisit UR7 (host logging).
2. The default length or the prompt cap is raised, or the demo is run on a CPU: add the KV cache.
3. Hugging Face changes the free-hosting conditions in a way that makes a public Gradio Space free.
4. A Gradio major version changes an API this app uses.
